## Repository Setup — read this first

This repo now pushes to **two remotes**, each seeing a different tree:

- **`origin`** — Alfonso's personal GitHub. `main` pushes here as always, full history, `.claude/`, `.context/`, `CLAUDE.md` all included. **This stays the working branch for every session** — nothing about day-to-day work changes.
- **`gitlab`** — the company-wide repo at `git.silversea-media.net/silversea-media/marketintelligent/ai-mi`, what the rest of the Silversea team actually clones and runs. A dedicated branch, **`gitlab-main`**, is what gets pushed there — it's `main` with `.claude/`, `.context/`, and `CLAUDE.md` untracked (still on disk, still tracked on `main`; just not part of what GitLab sees).

**Publish workflow, every time there's something ready for the team:**
```
git fetch gitlab                        # check GitLab's main hasn't moved since your last push
git checkout gitlab-main
git merge main                          # will conflict on .context/* modify-delete — resolve with `git rm --cached` (NOT plain `git rm`), keep files on disk
                                         # >>> before doing anything else, verify no previously-untracked files vanished from disk — see warning below <<<
git push gitlab gitlab-main:main
git checkout main                       # back to normal work
```
**Always `git fetch gitlab` and check `git rev-parse gitlab-main gitlab/main` match before assuming `gitlab-main` is current** — a teammate has direct push access and has now moved GitLab's `main` twice without going through this workflow (2026-07-21, 2026-07-22). See those dates' entries in `.context/DECISIONS.md`.

**GitLab's `main` branch is protected against force-push (confirmed live, 2026-07-22 — a force-push attempt was rejected by GitLab's pre-receive hook).** This is a permanent constraint, not a one-off: if an unwanted commit ever lands on GitLab's `main` again (whether from a teammate's direct push or otherwise), the only viable path is to merge it in and immediately follow with a corrective commit, then push forward normally — do not plan around rewriting or force-overwriting GitLab's history, it will be rejected.

**Warning, confirmed real 2026-07-22, check every time before/after `git merge main` into `gitlab-main`:** because `gitlab-main`'s history has `.claude/`, `.context/`, and `CLAUDE.md` recorded as *deleted* (from the original 2026-07-17 untracking via `git rm --cached`), a clean auto-merge of `main` will apply that same deletion to the **working directory**, not just the index, for any of those files `main`'s own side of the merge happens not to also touch. This isn't a one-time bug — it can recur on any future `main` merge and has already silently deleted 75 files from disk once (see 2026-07-22 incident below). After every `git merge main` into `gitlab-main`, confirm `.claude/`, `.context/`, and `CLAUDE.md` are still present on disk before pushing or doing anything else. If they're gone: `git checkout main -- .claude .context CLAUDE.md` restores them from `main`'s own history, then re-untrack with `git restore --staged .claude .context CLAUDE.md` (do NOT leave them staged/tracked on `gitlab-main`).

Full rationale in `.context/DECISIONS.md` (2026-07-17 entry for the two-remote design; 2026-07-22 entry for the force-push-protection and file-deletion findings). A GitLab personal access token was pasted into an earlier chat and had to be treated as compromised — revoked and replaced. The new token is never embedded in the remote URL or typed into a chat; it's cached by Git Credential Manager (Windows Credential Manager) after one manual authenticated `git fetch gitlab` in a real terminal. If push/fetch against `gitlab` ever fails with an auth error, that's a stale-credential problem to solve outside the chat, not something to fix by putting a token anywhere in a command or message.
