# Feature: Multi-Provider LLM Backend

**Base:** ad81ca161e35f148eb86bd9313e65d4bc4bda2f9

## Goal

Make `pipeline/analyst.py`'s LLM calls provider-agnostic and switch the default provider to one reachable from mainland China, so China-based Silversea teammates — currently unable to even generate a Groq API key from inside China (Groq's own site 403s there) — can run the pipeline at all, while keeping the backend genuinely swappable for testing other candidates against the existing Groq-based pipeline.

## Scope

**In scope:**
- A provider registry (extends `config/models.py`, not a new file) listing known LLM providers: Groq, DeepSeek, Qwen/DashScope, Kimi, and the existing local-Ollama path from `feature/002-local-llm-backend`. Each entry: key, display label, `base_url`, which env var holds its API key, default model name.
- **Default provider changes from Groq to DeepSeek** — confirmed reachable from mainland China without a proxy, cheapest, most generous free tier, lowest signup friction of the candidates researched.
- One generic "OpenAI-compatible remote" dispatch branch in `pipeline/analyst.py`, using the `openai` Python package parameterized by `base_url`/`api_key`/`model` — covers Groq, DeepSeek, Qwen, and Kimi with no per-provider branching, since all four are genuinely OpenAI-API-shaped. This supersedes `feature/002`'s Groq-specific `Groq(...)` client usage.
- Ollama/local branch reused from `feature/002` (native `ollama` package + its existing `SECTOR_SYNTHESIS_SCHEMA`/`SUMMARY_SCHEMA` JSON schemas), pulled into this feature's branch since `feature/002` was never merged to `main`. Its `_chat_completion()` dispatch-point pattern is the direct model for this feature's generalized dispatch.
- `main.py`: new `--llm=<provider_key>` CLI flag, parsed the same way as the existing `--domain=`/`--country=` flags (manual `sys.argv` scan, resolved once in the `if __name__ == "__main__":` block — **not** inside `run_pipeline()`'s per-country loop, since the backend choice applies to the whole run).
- New `LLM_DEFAULT` env var: when `--llm` isn't passed, `LLM_DEFAULT` (if set) selects the provider silently, no prompt, regardless of how many providers are configured — this is the "engineer-accessible, easily-changeable switch" for wherever the pipeline ends up hosted (GitHub-cloned dev machine, company server, cloud — one line in `.env`, no code change).
- Interactive picker, used only when neither `--llm` nor `LLM_DEFAULT` resolve a provider: a real popup window via `tkinter` (stdlib, no new dependency) when available, falling back automatically to a terminal prompt on *any* failure (missing display, missing tkinter build, anything — not a `DISPLAY`-env-var pre-check, which is Linux/X11-specific and wouldn't correctly detect headless Windows/Mac either). CLI-only surface, off `main.py` — explicitly not part of the Flask dashboard.
- Silent zero-friction default preserved: no `--llm`, no `LLM_DEFAULT`, exactly one provider's env var configured → use it, no prompt (today's behavior, unchanged for a single-provider `.env`).
- `requirements.txt`: add `openai`; pull in `ollama` from `feature/002`.
- `.env.example` and `README.md` updated — `DEEPSEEK_API_KEY` becomes the credential a fresh clone actually needs by default; document `LLM_DEFAULT` and `--llm`.

**Explicitly out of scope (recorded so it isn't re-raised as undecided):**
- **Zhipu/GLM** as a provider — real-name verification + Chinese-phone SMS gate blocks foreign signup, makes it a bad first candidate. Revisit only if leo.li specifically wants it added later.
- **Any Flask/dashboard-facing provider picker**, including an admin-page toggle with a user-supplied API key. Alfonso proposed this and then agreed to defer it after discussion: it needs real credential-storage security infrastructure this project doesn't have (the current admin auth is a single shared static password with no per-person audit trail — see `.context/STATE.md`'s "Explicitly deferred future work" section on real per-user access control), plus new persistence + "next pipeline run" hookup the admin page doesn't have today (it currently only approves sources, never influences pipeline runs). Log as a future idea once real per-user auth exists — don't re-litigate the security reasoning if it comes up again.
- **Re-verifying `feature/002`'s Ollama path.** It stays exactly as unverified as `.context/STATE.md` already records ("never verified against a real model on any machine"). This feature reuses its dispatch *shape*, not a claim that it works.
- **Anthropic/Claude Haiku production-switch implications.** Anthropic's API is also geofenced from mainland China (confirmed alongside OpenAI and Gemini during this feature's research) — meaning the long-deferred "Claude Haiku for production" plan in `.context/OVERVIEW.md` will hit the identical China-access wall if China-based users ever need production access, not just dev/test. Not this feature's problem to solve; flagged here so a future session doesn't rediscover it from scratch. Worth its own `.context/DECISIONS.md` note when this feature lands.

## Implementation Decisions

- **Default provider: DeepSeek, not Groq.** [User] — "since this can be accessed by everyone" (confirmed reachable from both mainland China and everywhere else, unlike Groq).
- **Provider registry lives in `config/models.py`, not a new file.** [Claude's default judgment, confirmed by user] — keeps the existing single-source-of-truth pattern `feature/002` already established for `GROQ_MODEL`/`LLM_BACKEND`.
- **One generic OpenAI-compatible dispatch branch (via the `openai` package) covers Groq/DeepSeek/Qwen/Kimi; Ollama keeps its own branch.** [Claude's default judgment, confirmed by user] — the four remote candidates are all genuinely OpenAI-API-shaped (unlike Ollama's OpenAI-compatible endpoint, which doesn't support schema-constrained JSON — the reason `feature/002` had to hand-write a native-`ollama`-library branch with its own JSON schemas). No reason to repeat that per-provider branching cost for providers that don't need it.
- **`--llm=<provider_key>` resolved once, before `run_pipeline()`'s per-country loop, mirroring how `--domain=`/`--country=` are already parsed in `main.py`'s `__main__` block.** [Claude's default judgment, confirmed by user via silence/deferral to technical judgment]
- **`LLM_DEFAULT` env var added as the "production-safe, no-prompt-ever" switch.** [Claude's default judgment, confirmed by user] — resolves Alfonso's ask that "whoever maintains the pipeline, wherever it's hosted" has an easily accessible way to pick the backend without needing an interactive session: it's a one-line `.env` edit, works identically whether the pipeline lives on a GitHub-cloned dev machine, a company server, or a cloud host — no dashboard, no new UI, no redeploy logic.
- **Popup fallback triggers on any failure (try/except around the whole tkinter path), not a `DISPLAY` env var pre-check.** [Claude's default judgment] — `DISPLAY` is Linux/X11-specific and would miss headless-Windows/Mac cases; wrapping the actual popup attempt is more robust and simpler.
- **Popup/prompt cancelled or closed with no selection made → abort the run cleanly, no silent fallback to a default.** [Claude's default judgment] — matches the project's standing "no guessing" rule; picking a provider the user didn't actually choose would be a worse failure mode than just stopping.
- **`--llm=<key>` naming a provider whose required env var isn't set → fail fast with a clear error before scraping starts.** [Claude's default judgment] — avoids burning scrape/filter time only to crash inside `analyse()`.
- **Admin-page LLM toggle with user-supplied API keys: deferred, not built.** [User, after Claude's pushback] — see Scope's "explicitly out of scope" section for the full reasoning; Alfonso explicitly agreed with the security/architecture objections raised during discussion.
- **Feature slug/number: `007-multi-provider-llm-backend`.** [Claude's default judgment] — 006 was the highest existing number under `.context/features/`; slug names the general capability (applies beyond just the China angle) rather than only the China-specific motivation.

## Global Constraints

- Every task in this feature must preserve the existing Groq path's exact behavior when `LLM_BACKEND`/`--llm`/`LLM_DEFAULT` all resolve to Groq — this is a generalization, not a rewrite; nothing about today's Groq-only single-provider `.env` setup should change behavior for someone who hasn't added any new env vars.
- Follow the project's "no comments explaining WHAT, only WHY" style already present in `pipeline/analyst.py` (e.g. the existing `_chat_completion`-style helper pattern from `feature/002` — reuse its comment style, don't rewrite it wholesale).
- `pipeline/analyst.py`'s existing grounding rules, prompts (`SECTOR_EXTRACT_PROMPT`/`SECTOR_SYNTHESIS_PROMPT`/`SUMMARY_PROMPT`), and the `_clamp_opportunity_scores()` safety net are untouched by this feature — this is purely about *which client sends the request*, not what's asked of the model.
- No new abstraction beyond what's needed: don't build a plugin system or dynamic provider-loading mechanism — a static registry list in `config/models.py` is sufficient for 5 known providers, consistent with this project's "simplicity first" / "don't design for hypothetical future requirements" principle.
- `feature/002-local-llm-backend`'s branch content (Ollama dispatch, `requirements.txt` entry, README section) should be pulled in and reused, not reimplemented from scratch — check its diff against current `main` for merge conflicts given it branched from an older commit (`168810e`, pre-dating Features 003-006).
- Verification-before-done applies as usual: DeepSeek's *correctness* (does the pipeline run and produce a sane report) is this feature's job to verify directly; DeepSeek's *China-network reachability* is explicitly NOT verifiable by this feature or by Alfonso — that's leo.li's independent, out-of-band confirmation (he's separately checking he can register a DeepSeek account and generate a key from inside mainland China). Don't claim "China-verified" in this feature's own REVIEW.md — that status depends on a confirmation this feature can't produce itself.
