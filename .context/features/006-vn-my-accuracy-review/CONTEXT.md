# Feature: VN/MY Accuracy & Code-Correctness Review

**Base:** 16db787

## Goal

Audit whether the three features shipped this session (Vietnam as a second country, Malaysia as a third country, full 7-domain activation) actually produce accurate, non-hallucinated report content and correctly-wired code — since all three `/feature-verify` PASSes verified code-matches-spec, not that the LLM-generated report content is factually grounded in real sources.

## Scope

Two distinct halves, both in scope, bundled into one feature (not split) because they're two audit lenses on the same three-feature body of work, not independent build features:

1. **Knowledge/accuracy review** — Do `data/latest_report_VN_BER.json` and `data/latest_report_MY_GENERAL.json` (both uncommitted/untracked generated artifacts, copied into this worktree from `../SilverSea_Market_Inteligence-domains` and `../SilverSea_Market_Inteligence-review` since they never existed in git history) actually reflect real information, with no hallucinated facts, entities, connections, or figures? Compare against:
   - `docs/Silversea_Vietnam_Market_07072026.pdf` and `docs/Source_submission_Malaysia_Sources.pdf` (original source lists, archived commit 851853b)
   - Freshly re-fetched live page content from the actual source URLs (see Implementation Decisions — no raw scraped content was cached anywhere on disk from the original pipeline runs, so this requires live re-fetching, not just reading a log)
   - This tests whether `pipeline/analyst.py`'s grounding rules (closed-book framing, quote-before-extract, "never invent facts") actually hold in real generated output, not just on paper.

2. **Code-correctness review** — Does the codebase actually wire source data through to report output correctly? In scope: domain filtering (`main.py`, `app.py`'s `_domain_mode()`), sector mapping, the keyword relevance gate (`pipeline/filter.py`) vs. the analyst's separate opportunities-gate keyword list in `SUMMARY_PROMPT` (do they actually agree on what counts as relevant?), RAG retrieval (`pipeline/vectorstore.py`), and the specific mechanical changes made this session (Vietnam's domain retagging in `config/sources.json`, the `SUMMARY_PROMPT` catalog/gate expansion, the 8-domain activation changes). Also explicitly in scope: sampling git history/diffs across `feature/003-vietnam-country`, `feature/004-malaysia-country`, and `feature/005-domain-activation` to review the actual rapid-subagent-driven work product, not just the current merged state.

### Explicitly out of scope
- No live pipeline run (`py main.py`) for verification — Alfonso wants that deferred until after this review, as its own separate next step.
- No new Groq API calls of any kind — this review must not touch the daily LLM quota. Live re-fetching of source *pages* (plain HTTP/Scrapling, no LLM) is fine and required; calling the LLM to re-analyze anything is not.
- No silent "fix while reviewing" — see Implementation Decisions on fix-task separation.
- This is `/feature-discuss` → `/feature-plan` only. No `/feature-execute` in this session — a separate Opus 4.8 agent executes the plan later, dispatched by Alfonso.

## Implementation Decisions

- **Bundled as one feature, not split**: Confirmed with the scope-check step — accuracy review and code-correctness review are two lenses on the same three already-shipped features, not independent build requests. Splitting would lose the shared grounding (git log sampling, source docs) both halves draw on. — Claude's default judgment, consistent with the handoff's explicit framing.
- **Re-fetch live source pages**: The plan MUST include task(s) that re-fetch current live page content from the VN/MY source URLs (reusing `pipeline/scraper.py`'s existing tiered fetchers — `_fetch_default`/`_fetch_stealth`/`_fetch_dynamic` — not a new scraping mechanism) to compare against claims in the generated reports. Confirmed: no raw scraped content, logs, or cache exists anywhere on disk from the original VN/MY pipeline runs — only the final report JSONs and the source-list PDFs survive. Without re-fetching, "grounded in real content" can only be checked against one-line source-list descriptions, not the actual article text the LLM saw. — User decision (asked directly, chose the re-fetch option over PDF-only).
- **Fix tasks are separate and optional**: Any finding that turns out to be a small, mechanical, low-risk fix gets its own separate, clearly-labeled fix task file, distinguishable from audit/findings tasks, so Alfonso can selectively execute them later (or not at all). Audit tasks never silently modify code — they produce findings documents. — User decision (asked directly, chose separate-fix-tasks over audit-only).
- **Deliverable format**: Findings are written as structured markdown audit documents under `.context/features/006-vn-my-accuracy-review/` (e.g. `ACCURACY-AUDIT.md` for the knowledge-review half, `CODE-REVIEW.md` for the code-correctness half), following this project's existing `REVIEW.md` convention — a findings table/list with severity, not prose narrative. — Claude's default judgment, matching established project convention (`.context/features/*/REVIEW.md` pattern already in use).
- **Workstream independence**: The accuracy review (reads report JSON + PDFs + live-refetched pages) and the code-correctness review (reads source code + git history) touch almost entirely disjoint files and can be planned/executed as independent task tracks with no shared-file ordering constraint between them, unlike e.g. Feature 002's Phase A which had to serialize because two tasks edited the same prompt file. — Claude's default judgment, based on file-ownership analysis.
- **Report scope is fixed by what's on disk**: Only `latest_report_VN_BER.json` (Vietnam, BER domain) and `latest_report_MY_GENERAL.json` (Malaysia, GENERAL domain) exist as generated artifacts — these are the only two reports to audit for the accuracy half. No Singapore reports are in scope (SG already has its own established accuracy baseline from Feature 001 and the original pipeline verification, not part of this review).
- **Git history sampling covers the actual rapid-dispatch work**: The code-correctness review must include reading `git log`/`git show` across `feature/003-vietnam-country`, `feature/004-malaysia-country`, and `feature/005-domain-activation` (not just the current merged code state) — this session's development happened via many cheap/mid-tier executor subagent dispatches, and Alfonso specifically asked for the actual work product to be sampled, not just the end-state diff.

## Preliminary Leads (unverified — planner/researcher must confirm or refute each, not assume proven)

Surfaced by a lightweight haiku-tier scan before this session started. Two were independently re-confirmed directly during this discuss session (see notes below); the rest are still open:

1. **CONFIRMED this session** — `pipeline/analyst.py`'s `SUMMARY_PROMPT` (~line 61) has no anti-hallucination grounding language, unlike its sibling prompts. Verified directly: `SECTOR_EXTRACT_PROMPT` contains `"GROUNDING RULE: Only state what is explicitly in the text."`; `SECTOR_SYNTHESIS_PROMPT` contains `"Only use facts from the text below. Never invent facts."`; `SUMMARY_PROMPT` contains neither — it goes straight from the product catalog into the OPPORTUNITIES keyword-gate instruction with no explicit "don't invent" rule, despite generating the highest-stakes output (opportunities with scores).
2. **CONFIRMED this session** — `app.py`'s `report()` fallback check (line 108-111) still hardcodes `for d in ("BER", "EDU", "GENERAL")` when deciding whether any domain-scoped report exists for a country, even though `_domain_mode()` (line 81-83) already validates all 8 active domains (`EDU, BER, GENERAL, RCC, HLS, MFG, CTE, PSS`). For a country/domain combination with no report where none of the original 3 domains have data either, this would incorrectly fall back to the stale legacy `latest_report.json` instead of showing "no report yet." Currently masked for VN/MY since both already have BER/GENERAL reports — worth fixing but not currently causing visible breakage.
3. **CONFIRMED this session** — `pipeline/analyst.py`'s `analyse(filtered_results: list, country: dict)` (line 339) takes no `domain` parameter at all, and `main.py`'s `run_pipeline()` never passes `domain_arg` into its `analyse(filtered, country)` call (line 71) despite having `domain_arg` in scope. `SUMMARY_PROMPT` instructs the LLM to reason about `product_fit` "from the domain the signal's sector belongs to" but the actual domain being analyzed (e.g. PSS, RCC) is never explicitly passed into the prompt as context. Worth checking whether this measurably affects product-fit reasoning quality in the real VN/MY reports, or whether upstream domain-filtered source content makes it moot in practice (i.e. does the LLM only ever see sources from one domain anyway, so it "guesses right" by construction?).
4. **Not yet checked** — `pipeline/weekly.py`'s `WEEKLY_PROMPT` allegedly still hardcodes "Singapore" in its framing text despite `generate_weekly_summary()` accepting a `country_code` parameter since Feature 003. Already logged in STATE.md as a known gap — confirm still true in the current code, decide whether it's in this review's scope to flag only or also produce a fix task.
5. **Not yet checked** — `pipeline/analyst.py`'s `os.environ["GROQ_API_KEY"]` (~line 341) allegedly raises `KeyError` if unset, unlike `feedback.py`/`weekly.py`'s graceful `os.environ.get(..., "")` pattern. Already logged as known in STATE.md — confirm still true.

## Global Constraints

- **Every subagent dispatch states an explicit model tier** — per CLAUDE.md's Subagent Strategy section, dispatch prompts must be generated via the `prompt-engineer` skill (task-file mode), which owns the tier↔model mapping. Given this is read-heavy audit work with real judgment calls (assessing whether an LLM output is "hallucinated" vs. genuinely grounded, and reviewing rapidly-generated code for correctness), lean toward higher-capability tiers for the actual audit-content tasks, not the cheapest tier — this mirrors the concern that motivated the review in the first place (rapid cheap/mid-tier dispatches produced the work being audited).
- **Explicit per-half model pinning (Alfonso directive, 2026-07-10 — supersedes the generic "lean toward higher-capability tiers" guidance above for Tasks 003-006 specifically):** the knowledge/accuracy-audit half (Tasks 003, 004 — comparing report claims against source text/PDFs) is pinned to **Sonnet 5**, not Opus — Alfonso judged this work doesn't need the top tier. The code-correctness/technical-review half (Tasks 005, 006 — reviewing this session's rapid cheap/mid-tier-dispatched code) is pinned to **Opus** — Alfonso specifically wants the deepest available analytical capability applied there, since that's the area he trusts least. The main `/feature-execute` dispatching/orchestrating session itself runs as Opus 4.8. **Feasibility note:** Alfonso's original request asked for "Opus 4.7 or 4.6" specifically for Tasks 005/006, distinct from the main session's Opus 4.8 (a three-way split: orchestrator on 4.8, technical review on a cheaper Opus point-release, knowledge work on Sonnet 5). This isn't implementable in this environment — the `Agent` tool's `model` parameter only exposes generation-level tier aliases (`sonnet`, `opus`, `haiku`, `fable`), not point-release pinning; `opus` currently resolves to Opus 4.8 regardless of which subagent requests it, identical to what the main session runs. Flagged to Alfonso and accepted; the two-way split (003/004 → `sonnet`, 005/006 → `opus`) implemented in each task file below is the closest feasible equivalent, and still captures the core intent: reserve the strongest available model specifically for the technical review, not spread evenly across both halves.
- **No Groq API calls, no live pipeline run** — hard constraint carried through every task in this feature; a task that would trigger `py main.py` or any `analyst.py` LLM call site is out of scope and must not be written into the plan.
- **Minimal impact / no silent fixes** — matches CLAUDE.md's Core Principles; findings get surfaced, not silently patched, except via the explicit separate opt-in fix task files described above.
- **Follow the `.context/` contract** — directory layout, file ownership, task status vocabulary (`pending | in-progress | done | blocked`), and commit policy all follow `~/.claude/skills/feature/references/context-contract.md` exactly as used by Features 001, 003, 004, 005.
- **This is a review of already-shipped, already-PASSed work** — all three source features (003, 004, 005) already have `REVIEW.md` PASS records. Findings from this review do not retroactively invalidate those PASSes (they verified code-matches-spec correctly); they surface a different, previously out-of-scope concern (content accuracy + rapid-dispatch code quality) that those reviews were never designed to catch.
